So multiple problems arose from the 9/12 design.

1. The cookie kept being invalidated. As it turns out, servers rotate the cookie every day or so so that a stolen credential isn't valid for very long.
2. `/home/notifications?filter=all` kept running into a bot detection page.
3. There's a ton of things that don't produce a notification, such as assignment titles, descriptions, due dates changing, material folder locations changing, messages, course updates, etc.

Plus, I increasingly ran into instances where I had to search through all materials to find relevant assignments based on a filter criteria.

### Keeping the cookie valid

Servers issue a Set-Cookie header whenever they want to rotate the old cookie. I could detect this cookie header and change it accordingly, but it's more reliable to use a cookie jar, which automatically manages cookies, expiration dates, and cookie rotation. `reqwest::cookie::CookieJar` should be able to handle the issue.

Unfortunately, the cookie _still_ rotates, as I'm currently using an active browser session's cookie, so the cookie may change when Foam is not running. I will see if the cookie jar works once I implement the onboarding for Schoology accounts, which will use a `wry` WebView to create a new session, isolating the cookies for use only in the application.

### Bot detection

Probably not too hard to implement via something like a headless scraper browser. There are tons of Chromium patches and whatnot that can simulate a real user very well. However, embedding a browser would inflate the bundle by a lot.

Instead, I'm simplifying to just use `/iapi2/site-navigation/notifications` and accept the 5-notification cap. It also simplifies things quite a bit, as that route always returns nice structured JSON.
