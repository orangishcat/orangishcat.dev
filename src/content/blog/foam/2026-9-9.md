Right now course information is stored as JSON files. I've decided to add Schoology API schemas as structs in Rust, allowing it to be easily serializable/deserializable in Serde while being type-safe.

Next, since I plan to support other LMS's in the future, I'm going to convert Schoology API types into standardized types for this project, preserving only the fields I need and making the API schema more intuitive. This is what will actually be saved into the filesystem.

So rihgt now courses are saved of a bunch of JSON files in your app data folder. Each JSON file is really just a raw JSON dump of the standardized `Course` type. By default, `serde` serializes nested objects pretty well, so I just left it like that.

I did a lot of deliberation about whether I should switch to SQLite or not.

Benefits:

- FTS (full-text search) support
- Super fast queries for just about any data type I add to SQLite
- Can support multiple active connections at once
  Drawbacks:

* It's extremely complicated compared to a JSON dump
* All the benefits of a database like the ones listed above just aren't that necessary at the scale of one client, maybe a few hundred course materials.
* Some basic optimizations might be enough, so a database is not necessary
* I've never worked with SQLite databases before beyond some basic exploration

Verdict: not yet. But as the project gets more complicated, I probably should.
