### Document viewer

Finally, the last feature before initial release. This was definitely quite painful to implement.

I had quite a few options to choose from this time. There are plenty of native options for rendering PDFs, including macOS Preview and browser options such as PDF.js. I could also open the document in an external application and leave that as a different problem.

What gave me quite a headache was office document support. There were many browser-based options, with varying quality and overall unreliable. Bundling LibreOffice was also not an option, as that would add many hundreds of MB to the build despite the entire application only being ~24 MB.

In the end, I chose to use a [WebView](https://en.wikipedia.org/wiki/WebView) using the [Wry](https://docs.rs/crate/wry/latest) crate. This WebView defaults to the operating system browser and supports all formats that a system browser can support, including PDF, images, video, audio, and more. There is no way to query what file types an operating system's WebView supports, so I just added a hardcoded list into the code.

![[./Attachments/Pasted image 20261006161441.png]]
For unsupported file types, which includes office documents, a message saying that the file type is unsupported appears as well as a button to open the file in an external application or in the file manager.
![[./Attachments/Pasted image 20261006165139.png]]
Office documents get a recommendation to install [LibreOffice](https://libreoffice.org). That message only appears when the file extension matches a hardcoded list of office document file extensions.

But there's yet another issue. When viewing through a WebView, it's as if you're viewing the page through your normal browser, which means that it is up to the server's discretion whether the file should be downloaded or not. What I want is the WebView to always display/preview the content no matter what.

I don't have a good solution for this. Making a network proxy that strips relevant download headers from the request response is very complicated, especially with additional edge cases such as `Range` requests (where browsers only request a subset of a document at once, such as for previewing large PDFs without downloading the entire thing) needing to be properly handled through the proxy.

Right now I download all files less than 15 MB, and just pass the link into the WebView for larger files. Schoology API servers ask the browser to download any files requested from their servers, so large files simply don't work with the document previewer as of now.
