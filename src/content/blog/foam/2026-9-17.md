I just migrated from JSON to SQL. I've been thinking of migrating ever since 9/9, and now I've finally done it.

### Why

The app needs a more efficient query system. I must manually go through every assignment and material to apply a predicate just to achieve basic functionality, for example filtering for overdue assignments. It gets exponentially worse when queries become more complicated. To see relevant assignment details based on an assignment id, I must iterate through all materials to find the assignment. But I need the course name of the assignment too. So I'd have to iterate through all courses to find the course name. The more advanced my queries get, the worse my searches become.

And FTS (full-text search) would be an entirely different beast.

But why not build some indexes? Use something like a hash map to map course ids to course objects, and boom, huge efficiency gains.

Well, build some more indexes and you've basically got yourself a database. It can handle all my querying needs, because that's what it was designed for.

Finding an assignment:
```sql
SELECT * FROM assignments WHERE course_id = ?
```

Selecting all assignment details in a user-friendly format:
```sql
SELECT a.*, COALESCE(c.course_title, a.course_id) AS course_title FROM assignments a LEFT JOIN courses c ON c.course_id = a.course_id WHERE a.course_id = ? AND a.id = ?
```
Simply put, this uses a [left join](https://www.w3schools.com/sql/sql_join_left.asp) so that a row returns not only assignment data but also course information (including the course name) for courses matching the condition `c.course_id = a.course_id`.

| id  | course_id | title | ... | course_title |
| --- | --------- | ----- | --- | ------------ |
|     |           |       | ... |              |
On the left is the assignment info, and the last column is the course title field we are looking for.

Oh and SQL supports FTS too.

## Database structure

Five major tables `materials`, `courses`, `assignments`, `notifications`, `sync_state`. Assignments references materials and contains additional information about the assignment, as assignments are much more commonly queried than any other type of material.

Misc data about any materials (e.g. document data) is stored in a `data` field, which simply holds a JSON dump of the remaining data.

`sync_state` acts like KV data storage, like a JSON file. The value is a column that stores JSON strings.

This approach does 3 things:
1. Allows important materials to be quickly and efficiently queried
2. Misc data as JSON reduces the complexity of managing the database schema
	- The only viable alternative is to create a relational database, adding a TON of complexity to a system that doesn't really need it
3. `sync_state` makes sure that all state is stored in the database (although it would probably be better as JSON... is subject to change)
	- (the config is JSON and is the only other file storing data as of now)
