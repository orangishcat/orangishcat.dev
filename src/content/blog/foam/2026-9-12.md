Today I'm setting up the most important functionality in the app: notification-based course syncing, and it's pretty complicated.

Yesterday I got the infrastructure for scraping notifications down. Now I need to process those notification objects and update the relevant course materials that have changed.

First I needed to set up a threading manager. This is because stuff like notifications and processing will _definitely_ need to take place on a separate thread. The main is reserved for quick operations, and worker threads do the bulk of the processing work.

The first change I made is to stop passing my app state around as a variable. Instead of

```rust
let state = AppState::default();
let ui = AppWindow::new();
state.sync_ui(&ui);
```

it now resembles my config, which is stored in a Mutex.

```rust
static STATE: LazyLock<Mutex<AppState>> = LazyLock::new(|| Mutex::new(AppState::default()));
```

To access:

```rust
pub fn state() -> MutexGuard<'static, AppState> {
    STATE.lock().expect("state lock is poisoned")
}
```

This makes it easier to access and also thread-safe. The bulk of the processing will happen while `state` is locked, and it will only need to be unlocked for assignment, which is a very short period of time. I just need to make sure not to deadlock on accident...

Next, the thread manager. `thread_manager.rs` essentially just stores a giant registry of thread handles. When a handle is dropped (i.e. the thread has finished running), the handle is dropped from the registry. When the application is closed, all the threads are joined before the application finishes shutting down.

But then shutdown became really slow when scraping notifications, so I also added a check_cancelled function:

```rust
static CANCELLED: AtomicBool = AtomicBool::new(false);

pub fn check_cancelled() -> std::io::Result<()> {
    if CANCELLED.load(Ordering::Relaxed) {
        Err(std::io::Error::new(
            std::io::ErrorKind::Interrupted,
            "shutting down",
        ))
    } else {
        Ok(())
    }
}
```

That way `check_cancelled()?` can easily break out of any function that returns a `Result` before it performs any more expensive operations, which mainly gets it to stop spawning any more network requests.

This is a lot of work already, but that was just the easy part. Now I have to actually scrape notifications...

The idea is to scrape notifications, then refresh the relevant materials that changed. In an ideal API, each notification response object tells you exactly what changed in which material. However, Schoology's notification system is far from ideal, which is not surprising considering Schoology API doesn't even expose a notifications hook and I'm using its internal API.

I ended up having to combine both the scraping methods that I made yesterday, instead of using one of them as a fallback. This is because `/home/notifications` doesn't expose new grade posts, only the top 5 does.

So whenever I receive a new notification:

- if it's a material posted notification, add it to its parent folder.
- if it's a new grade posted, scrape all grades for the course.

But it gets even more complicated.

- If the material posted is a document, calling Schoology API with its ID will return you a response with `course_fid`, telling you which folder the document is in.
  - However, it doesn't tell you which course it is in. Fortunately new material posted requests also gives you a link to the course it was posted in, so I only need to check the folders in the relevant course.
  - If the parent folder is missing, rescrape the entire course's folder hierarchy to find the folder and potentially find other missing folders as well.
- If the material posted is an assignment, Schoology API gives you **absolutely no way to tell where it is located**.
  - HOW IS THE API THIS BAD?
  - So either I could scrape the entire course when another folder arrives...
  - Or I can make another internal API call to the user-facing webpage of the assignment and fetch the folder link using `.content-top-upper-wrapper > div:nth-child(2) > div:nth-child(2) > a:nth-child(2)`.

So that's the notification parsing mostly working, but that's not the end of the story.

The course ID given by the notification can be WRONG.

As it turns out, notifications can occasionally give you the wrong section ID. If I am enrolled in Section 4 of a course, the notifications API will sometimes give you the section ID Section 2 of the same course. Like seriously?

Visiting the wrong section ID will still show you the contents of the course with the correct section ID, without changing the URL. I assume they had to somehow cobble together an internal redirect for whatever reason?

Calling the Schoology API with the incorrect section ID gives you ALL the basic info of the incorrect section, yet doesn't give you access to any of its contents (materials, updates, etc.)

So I had to compare the section title of the incorrect section to the section title of a section that was present in the actual data, and use that as the section ID instead.
